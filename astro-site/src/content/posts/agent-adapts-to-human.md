本周深度使用了 DeepSeek Harness，并对比了目前深度自用的 Agent 之一：pi。两者虽然产品形态不同，但都触及了一个关于 Agent 的核心问题：**究竟应该由人适配 Agent，还是由 Agent 适配人？**

这不是简单的产品易用性问题，而是两条不同的产品路线。

## 两条产品路线

### 人适配 Agent

Agent 内置更多能力、流程和约束，执行通常更受控、更稳定，也更容易开箱即用；但用户必须学习它的概念、界面和工作流，并逐步改变原有习惯。

### Agent 适配人

Agent 本身更轻、更泛化，用户不必大幅改变自己的工作方式，可以让 Agent 围绕个人习惯和业务流程进行组合与扩展；但自由度越高，需要自行补充的规则、工具、上下文和工作流也越多，对使用者的能力要求和初期建设成本更高。

结合实际使用体验，我对几类 Agent 产品的主观判断如下：

| 产品 | 人适配 Agent | Agent 适配人 | 使用体感 |
| --- | --- | --- | --- |
| Codex / Claude Code | ★★ | ★★ | 提供通用编码能力，但仍需在其交互与任务模式中工作 |
| WorkBuddy | ★★★ | ★ | 内置能力较强、开箱更直接，但个性化适配空间相对有限 |
| DeepSeek Harness | ★★ | ★★★ | 具备较好的扩展与适配能力，但补齐能力所需的门槛仍然较高 |
| Harness | ★★★ | ★★ | 内置 Board 和 Workflow，过程更受控，但用户需要适应其既定工作方式，深度定制同样有较高门槛 |
| pi | ★ | ★★★★ | 极致轻量、可塑性强，最接近「让 Agent 适配人」，但需要使用者自行建设工作流与能力体系 |

## 为什么我更推崇 pi 的方向

我并不把 pi 看作一个预先定义好流程、要求用户迁移习惯的完整软件。它更像电脑上的 zsh：

> 基础能力足够轻，使用者可以围绕自己的环境、工具和工作方式，逐步定义专属工作流。

它真正把主动权交还给人，让 Agent 成为个人能力的延伸，而不是新的流程约束。

当然，这种自由并非没有代价。它的门槛和建设成本同样很高——你几乎要自己搭起一套工作流与能力体系。

## 从落地的角度看，真正的摩擦在哪

从 Agent 应用落地、尤其是企业 AI Native 化的角度看，**减少落地摩擦的关键，不只是增加更多内置能力，而是让 Agent 能够适配个人工作习惯和企业既有业务流转流程。**

如果仍沿用传统软件工程的思路——先制作一套固定产品，再培训用户、培养用户习惯——Agent 最终可能只是另一套需要人去迁就的软件。

传统 SaaS 的逻辑是「定义流程 → 复制流程 → 培训用户适应流程」。但 Agent 是个体化的，每个人的工作方式、上下文和工具链都不一样，用统一的产品形态去覆盖，摩擦天然存在。

## 更合理的方向

保留必要的安全边界、稳定能力和治理机制，同时让 Agent 主动理解并嵌入已有流程，围绕岗位、团队和企业持续完成适配。

这条路可以拆成三层：

1. **安全与稳定是底线**：治理机制、权限边界、可观测性，这些不能因为「自由」而被牺牲。
2. **理解先于功能**：Agent 先读懂用户的上下文、习惯和既有流程，再用能力去补位，而不是把预设流程强加给用户。
3. **适配是持续过程**：适配不是一次配置完成，而是随着工作方式变化持续收敛。

## 结语

未来 Agent 产品真正的竞争力，可能不在于「预装了多少功能」，而在于：

> 能以多低的成本理解用户，并以多小的摩擦融入真实工作。

这是一条去中心化、反「平台化」的路。它把能力从产品手里交还给人，让 Agent 从「你要学会使用的软件」变成「长在你工作方式上的延伸」。
