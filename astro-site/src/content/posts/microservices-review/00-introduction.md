> 本篇是「微服务技术回顾」专栏的导读，介绍专栏的定位、结构和阅读方式。

## 为什么写这个专栏

微服务已经不是新名词。注册中心、网关、熔断、链路追踪、服务网格……这些词大多数后端工程师都听过、用过，但常常是**零散地**接触：项目里用了哪个组件就学哪个，遇到问题再查哪个。时间一长，知识点很多，却难以回答几个更根本的问题：

- 这个组件**解决的是什么问题**？没有它会怎样？
- 同类方案之间的**设计取舍**是什么？
- 这些组件之间**如何协作**，构成一个完整的体系？
- 什么情况下，微服务本身就是**错误的选择**？

这个专栏的目的，就是把这些散落的知识重新梳理一遍，串成一张有脉络的图。

## 专栏结构

专栏分为四个阶段，大致按「为什么 → 是什么 → 怎么管 → 值不值」的顺序展开：

| 阶段 | 主题 | 主要内容 |
| --- | --- | --- |
| 一 | 演进与拆分 | 单体的瓶颈、架构演进脉络、服务拆分原则与领域边界 |
| 二 | 核心组件 | 注册发现、配置中心、API 网关、RPC 与消息通信、负载均衡、熔断限流降级、分布式事务 |
| 三 | 可观测与治理 | 日志、指标、链路追踪，容器化与 Kubernetes，服务网格 |
| 四 | 复盘与反思 | 典型问题与设计取舍，什么时候不该用微服务，架构的下一步 |

## 写作方式

每篇文章尽量遵循同一个思路：

1. **问题先行**：先讲清楚这个组件或模式要解决的具体问题；
2. **原理与设计**：再讲核心机制，以及主流实现的设计差异；
3. **取舍与坑**：最后讨论适用边界、常见误用和实践中的教训。

重点放在「为什么这样设计」，而不是某个框架的 API 用法。

## 适合谁读

- 有一定后端开发经验，用过或准备使用微服务的工程师；
- 想把零散的微服务知识串成体系的读者；
- 需要做架构选型、想了解各方案取舍的技术负责人。

建议按章节顺序阅读；如果只关心某个具体组件，也可以直接跳到对应章节。
